## 3. Internal contradictions

**C1 — the completeness claim.** Line 680: "Everything else in Requirements 0–57 now has a mechanism." Against §2: Part D (23–28), Part E (30, 33), Part G (44), Part H (45, 51–53) and Part I (54–56) have none.

**C2 — access logging, removed in one place and retained in another.** Resource table, line 500: "``BackupBucket`` — lifecycle, policy, ownership, **logging**, update-replace". R38.1: "THE CloudFormation_Template SHALL NOT configure S3 server access logging on the Backup_Bucket", and R38.5 requires "a test … that the template declares no `LoggingConfiguration` on the Backup_Bucket and no second bucket". Either that cell is residue from the removed access-logging work, or the table declares a property the requirements forbid. Nothing else in the design mentions bucket logging, so residue is the likely reading — but as written the inventory contradicts R38.

**C3 — the "adds" inventory.** Overview: "The resulting architecture adds one small function, one SNS topic, one queue, and one comparison." The components table twelve lines later marks **four** items **new**: `Notifier_Lambda`, `Alert_Topic`, `Terminal_Queue`, `Suppression_Store`. Pass 4 adds a Notifier role, three log groups and the alert subscription. The suppression store is a new AWS resource the overview's count omits.

**C4 — maxReceiveCount.** Line 92: "a naive publish-on-every-catch would email once per attempt and then once more from the Notifier — **four emails** for one broken backup." Line 663: "With `maxReceiveCount` **bounded to 2**, a failing change costs at most 2 exports rather than 1." Two deliveries plus one Notifier email is three. The "four" arithmetic requires three deliveries.

**C5 — the free-tier figure is asserted and hedged in the same section.** Cost table: "SQS FIFO requests … **$0.00** *(free tier)*" and "**Total new recurring, at rest: $0.00**". Nine lines on: "The exact poller count is an AWS implementation detail, so this figure is an estimate to be **confirmed against the first month's actual bill rather than a guarantee**." 130,000 per queue per month is a single 20-second long-poller; Lambda's SQS event source mapping scales pollers, so 260,000 is a floor against a hard 1,000,000 ceiling. R11.10 asks the design to *name* the allowance the claim depends on — it does — but the table states as settled what the prose says is unconfirmed.

**C6 — the $1/month that never reaches the cost table.** Line 115: a customer-managed key "Costs roughly **$1/month**, which is a stated exception to zero-at-rest." The pass-4 cost table has no KMS line and no contingency note, and totals $0.00. R57.4 requires any recurring charge to be "stated, justified and quantified in the design against prices retrieved from the AWS Price List API" — this one is estimated in prose, in a different pass, and omitted from the table that R57.5 demands.

**C7 — the cost table depends on a parameter the template inventory omits.** Cost table: "S3 archive storage, Standard … **first 60 days**" and "S3 archive storage, Glacier Flexible … **days 60 → retention**". The parameter list (line 503) contains no transition-days parameter and no `LongTermStorageClass`, which R42.10, R42.11 and R34.7 all require by name. The storage cost model is computed off a lifecycle transition the design never declares.

**C8 — "three-year retention" is asserted, never configured.** Line 200: "a **three-year retention** gives roughly 25–75 objects — two orders of magnitude below the 1,000-key page limit. **One request, permanently.**" Pass 4 exposes `BackupRetentionDays` as a bounded parameter with no stated default, and R34.9 requires its minimum be tied to "the longest quiet interval the design records" — which the design never records. The claim that one LIST request suffices forever rests on a retention value that exists nowhere in the document. (The object arithmetic itself is consistent: pass 4's "8–25 backups per year" × 3 = 24–75.)

**C9 — the listing algorithm has no prefix, but two criteria require one.** Pass 2: "**A flat listing, no delimiter, no prefix walk**", and the code passes only `Bucket`, `MaxKeys`, `ContinuationToken`. R9.19: "THE Filter_Lambda SHALL accept the Last_Update_API endpoint **and the bucket listing prefix** through configuration, so criterion 10.4 can create a coverage gap for verification without deleting an archive." R10.4's sanctioned route is "pointing the listing prefix at an empty prefix". As specified, that verification route cannot be exercised — and the design covers only the endpoint half of 9.19 ("The Last_Update_API URL is a fixed template parameter").

**C10 — the marker-object rejection rests on a policy shape the requirements forbid.** Pass 2's rejected-alternatives table: an S3 marker object "**trips the encryption-header policy in criterion 37.2**". R37.2 requires that policy be written so it "cannot deny the Backup_Lambda's own upload", and R37.3: "the policy SHALL be expressed as a **mismatch test rather than an absence test**". A marker written without an SSE header is an absence, not a mismatch, so under the required shape it does not trip. The argument is sound only against the policy R37.2 explicitly rejects — and the design never specifies the policy at all (see §2, R37).

**C11 — the ListBucket grant, pre-existing or new.** Pass 3, line 436: `ListObjectsV2` "needs only `s3:ListBucket`, which the function **already holds for nothing else**." Pass 4 grants the Backup role "`s3:ListBucket` **for the verification**", which is R40.8's and R13.6's stated purpose. The verification is the sole reason the grant exists; "already holds" reads as pre-existing.

**C12 — the Notifier's remit, two or three or four.** See the last row of §1.

**C13 — the flow diagram implies an action no grant covers.** The mermaid edge `R -. cannot process .-> T[Terminal_Queue]` puts the Notifier_Lambda writing to the terminal queue. The pass-1 decision table and R7.5 put the terminal queue behind the Dead_Letter_Queue's own `RedrivePolicy` — SQS moves the message, the Notifier never sends it. The pass-4 Notifier role correctly holds no `sqs:SendMessage`. The IAM is right; the diagram is wrong.

**C14 — `NotifierLogGroup` is declared twice** in the resource table: once inside "`NotifierLambdaFunc` + role + log group" and again in the cell "`BackupLogGroup`, `FilterLogGroup`, `NotifierLogGroup`".

**IAM grants vs mechanisms — otherwise clean.** Every action the three functions perform in passes 2–3 has a matching grant, and every grant maps to an action: Filter (`sqs:SendMessage`, `s3:ListBucket`, `lambda:InvokeFunction`, `ssm:GetParameter`/`PutParameter`, `sns:Publish`+KMS, log group) ↔ enqueue, listing, async destination, suppression store, coverage-gap publish; Backup (three SQS service actions, `s3:PutObject`, `s3:AbortMultipartUpload`, `s3:ListBucket`, `ssm:GetParameters`, `sns:Publish`+KMS, log group) ↔ ESM polling, multipart upload, verification listing, tokens, caught-failure publish; Notifier (DLQ consumption, `sns:Publish`+KMS, log group) ↔ its two envelope shapes. The conditional SSM decrypt grant is handled correctly per R40.3/40.4. Deliberate withholdings — no `s3:GetObject` anywhere (40.9), no `s3:ListBucketVersions` on the Filter (9.18), no Backup grant on the DLQ (2.4) — are all consistent across passes.

**The design states no resource count.** There is no "25 resources" claim in the document to check — the brief's figure is not in the file.
