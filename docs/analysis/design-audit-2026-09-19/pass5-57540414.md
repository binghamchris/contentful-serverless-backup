## 2 · Fixes that are technically wrong, or that introduce a new error

**2.1 · 5.2's suffix fix is unimplementable for the verification-failed case, which is half of what it claims to close.**

5.2 says: *"A partial or unverified archive SHALL be written under a key the `ARCHIVE_KEY` pattern excludes."* For the rate-limited partial (adversarial E1) that works — `…123Z.partial.zip` genuinely fails `/…\.\d{3}Z\.zip$/`, and the shortfall is known before the upload. For the verification-failed archive (E2) it cannot work. I traced the current handler: `/Users/chrisbingham/Documents/GitHub/contentful-serverless-backup/backup-lambda/index.js` lines 101–102 compute the key from `new Date()` at the *start* of the handler, and verification happens after the upload completes. You only learn the archive is bad once it is already stored under the conforming key. Renaming needs `CopyObject`, which requires `s3:GetObject` on the source — forbidden by criterion 40.9 — plus a delete no role holds. The only implementable routes are to upload twice (extra PUT and transfer) or to relax 40.9, and pass 5 chooses neither while presenting the fix as free.

The `Size`-floor half does not rescue E2 either: a *floor* catches truncation, not the size **mismatch** verification actually detects. 5.2 concedes a "nonzero-but-wrong-size" residue but the sentence quoted above still claims the unverified case is closed.

**2.2 · 5.2 reverses criterion 15.4's purpose and creates an unbounded export loop.**

Because a `.partial.zip` archive never satisfies coverage, every subsequent build of either site re-enqueues a full export. Under a *persistent* rate-limit condition — a space simply too large for the quota, which is the case 15.4 was written for — that is one full Contentful export per build, indefinitely, plus a coverage email per re-notify interval. 5.2 frames this as "the deferred retry the 'wait for quota' remedy wanted" and puts no bound on it. It directly contradicts 5.6's claim that `maxReceiveCount: 2` "caps failure-path quota at two exports", and it is the exact behaviour ("retrying when quota is the constraint is the worst available move", pass 4) the design elsewhere forbids. Related: those `.partial.zip` objects are now never expired, because 5.5 removes current-version expiry.

**2.3 · 5.11's ~150-day retention bound is applied to a parameter 5.5 just made inert, and the real exposure is left unbounded.**

5.5: the lifecycle "SHALL NOT expire current object versions at all". 5.11: "`BackupRetentionDays` SHALL be bounded so no permitted value places an object in Glacier Flexible Retrieval for less than its 90-day minimum given the 60-day transition — i.e. a minimum retention of ~150 days." Those cannot both stand. If current versions are never expired, `BackupRetentionDays` governs no deletion, so no current version can ever incur an early-deletion charge and the bound is unnecessary; meanwhile the only objects that *are* deleted are noncurrent versions, governed by `NoncurrentVersionRetentionDays`, which 5.11 does not bound at all. Pass 5 also never says what `BackupRetentionDays` now does, or whether it is retained as an inert parameter. Both halves of the fix land on the wrong parameter.

**2.4 · 5.1 creates a second writer to a last-write-wins JSON blob, so fields can be clobbered.**

The store now holds four fields and is written from two different decision paths (on enqueue, and on notify). With last-write-wins and no CAS, an invocation that read before another's write can overwrite the *other* field: a lost `enqueuedContentChange` produces an email for a backup that was just enqueued; a lost `notifiedContentChange` produces a duplicate email. Pass 5 inherits pass 2's "the race is benign" claim, which was about two near-identical writes of one field and no longer describes the mechanism.

**2.5 · 5.1's grace-bounded suppression and the DLQ path can both email for one incident.**

A killed backup emails via the DLQ at ~3 hours (5.6's own figure). 5.1's suppression lapses after the grace period — default 30 minutes. So a build occurring 30+ minutes after the content change produces a coverage-gap email, and the same failure produces a phase-tagged failure email 2½ hours later. Two emails, two mechanisms, one incident. Pass 5 does not deduplicate between the coverage path and the failure path, and does not count this against criterion 7.10 or 57.13.

## 3 · Fixes where the headline is right and a sub-part is missed

- **5.9's budget omits the two calls pass 5 itself added.** Its work list is "a cold start with four SDK clients, a fetch with retries against two endpoints, an S3 listing, an SSM read, and possibly a publish and an SSM write." Missing: the SQS `SendMessage` that is the Filter's primary job, and the *new* `PutParameter` that 5.1 requires on every enqueue. The "other half" of the 30 s budget must therefore cover a four-client cold start plus up to six AWS calls in 15 s, and 5.9 allocates that half rather than computing it — which is what criterion 16.9 asks for.
- **5.3 does not say what happens when one of the two endpoints fails.** "Maximum across both" is the right operator (a stale input cannot freeze the comparison, and an erroneously-high value fails safe toward more gap reporting, not less). But if both fetches must succeed, one site's outage sends every build down the fail-open path — an export per grace window, indefinitely, silently.
- **5.4 widens the `indeterminate` state without addressing adversarial N's latch.** An unparseable key is a correct new route into `indeterminate`, and criterion 9.9 makes `indeterminate` never notify. Pass 5 adds a way in and no way out; sustained indeterminacy across N builds is still a permanent silent-failure state by design.
- **5.12 converts "no mechanism" into "named as in scope", which does not discharge a design-record obligation.** Requirements 23.3, 23.4, 23.7, 24.3, 24.6, 25.3, 44.4 and several of 54–56 are explicitly "THE design SHALL record/state …". I read them: 23.3 wants the `nodejs20.x` deprecation dates and why the *update* block is operative; 23.4 wants why 24 over 22; 23.7 wants how the runtime change is validated inside the quota constraint; 24.6 wants whether the new major changes request count. None appears. A task list cannot satisfy a clause addressed to the design, and 5.12's framing invites a task-writer to treat them as settled.
- **5.5 says "steady-state".** With no current-version expiry, storage grows monotonically forever — roughly 1.25 GB/year at 25 backups of ~50 MB. The number is immaterial for a decade, but Requirement 34's bounded-growth intent is now met by growth being *slow*, not bounded, and 5.5 should say so plainly. Criterion 34.10's test is also not named.
- **Pass 2's cost table is now stale** — "SSM `PutParameter`: only when notifying" — because 5.1 writes on every enqueue. Harmless (standard throughput is free, and Parameter Store auto-rotates the oldest of 100 versions) but uncorrected.
- **5.6 omits `LogRetentionDays`' enumerated `AllowedValues`**, still deferring to "the set CloudWatch Logs accepts", which is the same gap the implementability audit raised.
- **5.11 fixes only half of a41's A9.** The 90-day early-deletion half is addressed (however see 2.3); the per-1,000 **lifecycle transition request** charge is still absent from a cost table that claims to enumerate per-item recurring cost.
- **5.11's cross-reference list stops short.** It fixes `42.10→42.13`, `36.9→36.15`, `16.9→16.12`, `40.8→40.9`, `7.9→7.11` and the Notifier's "two"→three. It leaves `39.2`, `36.4→36.6`, "Requirement 47's twelve", and 57.5's "three items". It also *states* the flow diagram's `Notifier → Terminal_Queue` edge is wrong without the diagram being corrected — defensible for a supersede-on-conflict pass, but a reader of the diagram is still misled.

## 4 · New factual claims pass 5 introduces — verified, wrong, unverified

**WRONG (verified).** *"Backup_Lambda `Timeout` **900 s** — The Lambda maximum."* 900 s is the maximum for **on-demand** capacity mode. On 9 September 2026 — ten days before pass 5 — AWS raised the function timeout to **90 minutes (5,400 s) for asynchronous and event-source-mapping invocations on Lambda Managed Instances**, which is precisely this design's invocation path. The blog states "There is no additional charge for using the 90-minute timeout. Standard Lambda Managed Instances pricing applies", and closes by inviting requests for a longer timeout "for the on-demand capacity mode", confirming on-demand is still 15 minutes. 900 s is almost certainly still the right *choice* (LMI is an EC2-style capacity mode, against zero-at-rest), but the justification is now false, and the entire timing chain plus the accepted 3-hour crash-notification latency is derived from it. This is exactly the failure mode pass 5's own preamble names.
- [Announcing 90-minute function timeout on AWS Lambda Managed Instances](https://aws.amazon.com/blogs/compute/announcing-90-minute-function-timeout-on-aws-lambda-managed-instances/)
- [Configure Lambda function timeout](https://docs.aws.amazon.com/lambda/latest/dg/configuration-timeout.html) — 900 s maximum

**Now resolvable, and the answer is NO (verified).** *"Verify before the task list is written: whether `contentful-export` v8 is ESM-only."* It is not. The published package declares `"main": "dist/index.js"`, no `"type": "module"`, and `"engines": { "node": ">=22" }`; the README documents **both** a CommonJS `require('contentful-export')` and an ESM `import` form. So the existing CommonJS handler keeps working and the ESM conversion drops out of the atomic change set. Worth recording the adjacent constraint: Lambda disables `--no-experimental-require-module` on `nodejs24.x`, so *had* it been ESM-only, `require` would have failed and the `NODE_OPTIONS` escape hatch forfeits the Lambda SLA.
