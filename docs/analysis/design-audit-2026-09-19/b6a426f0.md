I'll read both documents first. ## Verdict

Not yet handoff-ready. The design is unusually strong on *mechanism* — the Coverage_Check, the asset reconciliation, the log-group migration and the inert-conditional pattern are all specified to the point where a coding agent could implement them from the text. It is weak on *values* and on *the atomic change set it says is atomic*. A task-writer working from this document alone would have to invent roughly fifteen load-bearing choices, and two of the requirements' obligations cannot be discharged as written.

The design is honest about two open items (KMS grant sufficiency, sizing envelope). It is silent about a larger set that it treats as settled.

## Priority findings — the implementer must invent these

**P1. The atomic change set names none of its four packages.** The design's closing paragraph says the runtime upgrade, export-library major, archive-library replacement and streamed upload land together. It never writes `nodejs24.x` (only requirement 23.1 does), never commits to contentful-export 8.x (the string `8.5.0` appears once, inside an illustrative manifest JSON blob — that is an example payload, not a version decision), and never names adm-zip at all. `archiver` appears only as a word in the pipeline arrow `archiver → stream → Upload` and in the prose "the archiver enumerates before the output file exists" — no version, and no explicit statement that it *replaces* adm-zip rather than joining it. Requirement 26.1 asks for an adm-zip upgrade and 26.2 permits a replacement instead; the design never says which happened, so a task-writer cannot tell whether to write one task or two. Requirements 23.3, 23.4, 23.7, 24.3 and 24.6 each say "the design SHALL record" something about these upgrades (deprecation dates, why 24 over 22, how the runtime is validated inside the quota constraint, how far behind the lockfile is, whether the new major changes request count) — none of the five appears.

**P2. "The configuration SHALL retain the newest archive unconditionally" (34.9) has no mechanism, and S3 lifecycle has no primitive for it.** The design's only answer to 34.9 is the retention *minimum*, and it never states the minimum, nor the "longest quiet interval" figure the minimum must exceed. Requirement 34.10 demands a test asserting unconditional newest-archive retention. A task-writer will either write a task that cannot be completed, or silently reinterpret 34.9 as "set a long minimum and hope". This needs a design decision before tasks.md: either accept that the minimum is the whole mitigation and amend 34.9, or specify a mechanism (tag-based lifecycle exclusion applied by the Backup_Lambda — which would need `s3:PutObjectTagging`, forbidden in spirit by Requirement 36's immutability intent and not in any role's grant list).

**P3. The KMS-grant acceptance test does not test the grant.** The design gates the `kms:ViaService` identity-policy grant on "criterion 10.1's test publication". Criterion 10.1 is a publication confirming the subscription works. If the operator issues it with `aws sns publish`, it exercises the *operator's* credentials, not the three Lambda execution roles' identity policies — which is the thing asserted-not-proven. The acceptance test has to be a publish *performed by each of the three roles* (the induced failures in 10.2/10.3 cover Backup and Notifier; nothing covers the Filter's coverage-gap publish). The design does not say this, and its fallback ladder therefore never gets triggered by a passing-but-vacuous test.

**P4. The update-window parameter is silently abandoned.** Requirements 18.6, 42.5 and 42.6 all treat an existing update-window parameter as live: 42.5 requires its minimum be bounded by the worst-case observed Amplify build duration for each consuming site, with those measured durations recorded *in the design*, and 42.6 makes it the named carve-out to criterion 0.3's no-default-changes rule. The design's enqueue table replaces the window entirely with a content-timestamp-versus-archive-key comparison and never mentions the window, the measured build durations, or whether the parameter is retained. Criterion 0.3 forbids removing an existing parameter. A task-writer must decide whether to implement a mechanism the design replaced, retain a now-inert parameter, or breach 0.3.

**P5. The whole queue-timing triple is absent.** Requirement 3.1 expresses retention as a *factor* (≥ 2 × VisibilityTimeout × maxReceiveCount) specifically so it is assertable, and 3.3 keeps VisibilityTimeout ≥ 6 × Backup_Lambda Timeout. The design gives `maxReceiveCount = 2` once, in prose in the quota-budget section, and gives no VisibilityTimeout, no MessageRetentionPeriod, and — most consequentially — **no Backup_Lambda `Timeout` anywhere in four passes**. Every number in the chain derives from that one. Requirement 3.2 also requires `maxReceiveCount` declared as a bounded parameter; it is missing from the design's new-parameter list. Requirement 3.7 requires the design to state worst-case notification latency per failure class, which is a direct function of these values — absent.

**P6. The Amplify status regex is not given.** The design supplies the `ARCHIVE_KEY` regex in full, which makes the omission conspicuous: step 2 of the decision sequence says only "Anchored regex on the message body." Requirement 21.1 requires "a single documented, anchored regular expression with a capture group", and 21.2 makes the committed fixture load-bearing. The design quotes no Amplify message text, so the pattern *and* the fixture must both be invented against a format nobody has written down. Same section: "Leftmost DNS label of the app URL, Amplify-sanitised" names the branch rule without documenting the sanitisation (21.5 requires the rule documented; Amplify does more than slash→hyphen — it lowercases, folds other non-alphanumerics, and truncates).

**P7. The listing has no prefix, but 9.19 requires one.** The design's `newestArchive(s3, bucket)` takes no prefix argument and the surrounding text argues *against* prefixes ("A flat listing, no delimiter, no prefix walk"). Criterion 9.19 requires the listing prefix to be configurable precisely so verification step 10.4 can manufacture a coverage gap by pointing at an empty prefix without deleting an archive — and 10.4 names that hook as the reason no role holds delete permission. As written, the design removes the only sanctioned route to verifying the Coverage_Check.

**P8. `MessageDeduplicationId` derivation is unspecified.** The flowchart says "dedup id = content state" and criterion 20.1 requires it derived from content state. The actual derivation is load-bearing: it must be byte-identical across builds of *two different frontends* observing the same content state, must fit SQS's 128-character limit and allowed character set, and criterion 9.21 requires the coverage-gap email to embed a manual enqueue command carrying the same value — so an operator has to be able to compute it by hand. Hash of the ISO timestamp, the raw timestamp, or something else is never said.

On the two deferred ones: the deferral is sound in principle but **circular as written**. The commissioning export runs on the deployed function, so `MemorySize` and `EphemeralStorageSize` need values *before* it can execute. The design gives no interim pair and never states that this is a two-pass deployment (deploy with interim values → commission → edit template → second stack update). Note also that neither is a parameter in the design's parameter list — 16.5/16.6 treat them as properties with inline-comment rationale — so "feeding the measurement back" means a template edit and a stack update, which the design never says.

## 3. Sequencing

What the design does give: the ESM-disabled-on-first-deployment rule, `DependsOn` from each function to its log group, and the four-item atomic change set. That is a good start and a task-writer can use it.

Ordering constraints the design implies but does not state:

- **Queue timing must land with or before the fail-loudly change.** Today retention (900s) < visibility (1800s), so a thrown invocation's message is purged before redelivery. Ship Requirement 1 first and the DLQ path — and therefore the Notifier and every uncatchable-failure email — is still unreachable. These are two different requirements and a naive task order puts them in separate commits.
- **The DLQ→Notifier ESM has no disable gate.** The `EventSourceMappingEnabled` parameter is described (4.5) as controlling *the Backup_Lambda's* mapping. So on a first deployment the DLQ mapping is live against placeholder Notifier code, which now throws — every dead-lettered message would walk straight to the Terminal_Queue with no email. Either the parameter covers both mappings or a second parameter is needed; the design decides neither.
- **Notifier before its two consumers.** The Filter's `OnFailure` destination and the DLQ's ESM both reference the Notifier. `DependsOn`/`!GetAtt` probably handles it, but the design never states it, and the Filter's `lambda:InvokeFunction` grant is a third edge.
- **Subscription confirmation is a manual, asynchronous gate.** Criterion 6.6 says CloudFormation reports success regardless. Every verification step in Requirement 10 — including the KMS acceptance test the design gates the whole notification channel on — is blocked until a human clicks a link. Not sequenced.
- **Commissioning test publication vs commissioning export.** The design orders neither. If the export runs first and succeeds, no publish occurs and the KMS grant stays untested; if it fails, the failure email depends on the untested grant.
- **Queue rename requires a drained queue** (41.5), so it cannot be bundled with a change that is likely to have messages in flight.
- **IAM log-group scoping moves with the log-group cutover** (5.8, 40.2) and `logs:CreateLogGroup` is removed at the same time (5.9) — a task that reorders these locks a function out of its own logs.
- **The orphaned-log-group deletion** is a post-deployment manual step; the design states it exists but does not place it in the ordered procedure.

## 4. Testability hooks

**The Coverage_Check pure function does not have six inputs.** `(contentTs, archiveOutcome, now, grace, skew, suppressionState)` cannot evaluate the design's own third notification condition — "this invocation is not enqueueing a backup for this same content state" — because the enqueue table depends on `statusCaptured` and `branchMatches`, neither of which is an input. Nor can it apply the re-notify interval, which is config rather than stored state. Criterion 47.7 (enqueueing invocation must not notify) and 47.10 (check runs on a non-matching branch) are exactly the tests that need the missing inputs. Either the signature grows to eight, or the pure function must return both decisions and take the raw inputs. A task-writer will pick one and may pick the one that makes 47.7 untestable.

**The injectable working root is asserted, not located.** "The working root is injectable" and 48.1's "through configuration" leave open environment variable, handler argument, or module constant. Naming it matters because 48.4 forbids stubbing `fs` or the archiver, so the test drives the real handler and needs the real knob.

**Asset reconciliation is genuinely concrete** — the expected-path derivation, the protocol-relative `//` case, the `decodeURIComponent` on the pathname, and the missing/zero-byte split are all in code. This is the best-specified test surface in the document, and the fixture it needs is unambiguous.

**Missing fixture.** Requirement 51 lists four fixtures; the asynchronous invocation record is not among them, yet 8.3 and 22.6 require the Notifier to discriminate that shape from the SQS batch, and pass 1 makes a specific claim about it ("the record contains no log stream identifier at all") that only a fixture can hold the implementation to. The design names no fixture for it.

## 5. The commissioning export

Named, motivated, and counted in the quota budget — but not specified. What a task-writer needs and does not get:

- **What it runs.** Direct `Invoke` on the Backup_Lambda, or a manual enqueue through the queue? The two differ: only the enqueue path exercises the ESM, the dedup id and the `ApproximateReceiveCount` gate.
- **Against what.** Production space is implied (the envelope must be real), but Requirement 41.6 and the governing constraints are hostile to non-production stacks touching production, and the design never says which stack performs it.
- **An internal contradiction.** Pass 3 says it "records the largest limit that actually succeeds for this space". Finding the largest limit that succeeds is a search, and a search is several exports — against "the only export in this design not triggered by a content change" and "no further untriggered export SHALL be performed" (16.12). If the intent is one export at a high configured limit that adaptively halves and reports where it settled, the design should say so, because that is a different measurement with a different answer. As written, a task-writer must either breach the one-export authorisation or invent the single-run method.
- **Where its outputs land.** No file path, no schema. Requirement 16.11 wants the envelope in the design and the documentation with its failure symptom; 16.12 wants it in the decision record; 10.9 wants verification results under `docs/`. Three destinations, no names.
- **How outputs reach the template.** Since `MemorySize` and `EphemeralStorageSize` are properties rather than parameters, feedback is a code change plus a stack update. Never stated, and it is the second half of the chicken-and-egg noted above.
- **Whether it exercises the KMS grant.** It does not, on the success path — see P3.

## Minor but worth fixing before tasks.md

- Criterion 0.7 cites **16.9** as the authorising criterion for the commissioning export; 16.9 is the Filter's time budget and **16.12** is the authorisation. A task-writer chasing the citation lands on the wrong requirement. The design compounds this by citing 0.7 in both directions.
- Requirement 13.5 cites "criterion 40.8's prohibition on `s3:GetObject`"; the prohibition is 40.9 (40.8 is the Backup role's grant list). The design gets this right, so only the requirements need the fix.
- Criterion 13.4 requires a checksum algorithm and a content type on the upload. The design discusses composite multipart checksum *semantics* at length but never names the algorithm or the content type.
- `timestampFromKey` is referenced and not defined; recoverable from the regex, so low risk.
- `SubscribeAlertEmail` default is unstated. If it defaults true, a validation stack per Requirement 41 emails the owner unless the operator remembers to override — the opposite of 6.4's intent.
- The design's new-parameter list promises "every one of which carries a default" and then gives not a single default value. Requirement 33.4 requires every parameter documented with its default and permitted values, and 33.6 requires a test asserting the documented list matches the template exactly — that test cannot be written from this design.
