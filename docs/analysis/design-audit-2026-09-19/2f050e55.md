## A. CRITICAL — Enqueue-suppression silences the only detector whenever the enqueue never becomes a backup

**Scenario.** Coverage notification condition 3 is *"this invocation is **not** enqueueing a backup for this same content state."* Per the enqueue table, any success + matching-branch + usable-timestamp build where the archive is older than the content **always enqueues**. So on every production build where a gap exists, the coverage email is suppressed — unconditionally, on the assumption that the enqueue closes the gap.

Now break the path *between* the enqueue and the export: `EventSourceMappingEnabled: false` left at `false` after a first deployment (criterion 4.6 instructs exactly that ordering), the ESM deleted or mis-wired, `ReservedConcurrentExecutions` set to 0, the FIFO group wedged, or the backup function replaced by the throwing placeholder. SQS accepts the message (SendMessage succeeds), the Filter suppresses the coverage email, the Backup_Lambda never runs, and every subsequent build repeats the cycle: content still newer than the newest archive → enqueue → suppress.

**Concrete misbehaviour.** The system has **no backup at all and never will**, and it emails nothing — forever. The caught-failure path needs the Backup_Lambda to execute; the DLQ path needs receive-count exhaustion, which needs deliveries. Neither fires. This is the full-system-failure case and it is silent.

**Do the stated mitigations cover it?** No. The design's "What no path covers" section records only the case where the Filter is *never invoked*. Here the Filter is invoked, works correctly, observes the gap, and is silenced by its own suppression rule. Criterion 9.10 was written as "the same invocation is closing the gap" — the design implements "the same invocation *intends* to close the gap", which is a different and much weaker statement.

A second consequence worth noting: because matching-branch builds always suppress, a real persistent gap is reported **only on non-matching-branch builds** (which don't enqueue). Detection of the most severe failure mode is therefore contingent on how much feature-branch build traffic the two sites happen to produce.

**Fix.** Make suppression time-bounded and stateful rather than instantaneous. The suppression store already exists — extend its value to `{ enqueuedContentChange, enqueuedAt }` and change condition 3 to: *suppress only if an enqueue for this same content state was made within the grace period.* On the next build after grace has elapsed with the archive still absent, notify. That single change closes A, and it also fixes the "backup in flight" case properly (see **G**) because the grace period becomes the arbiter instead of an unconditional veto.

## B. CRITICAL — The Coverage_Check's content input is produced by the very pipeline whose failure it exists to detect

**Scenario.** The Last_Update_API is the website's own static build output, read from a **fixed** endpoint — production's, for one of the two consuming sites. Both sites' build notifications invoke the Filter, but the content timestamp always comes from site A's published JSON.

Content changes at 10:00. Site A's build fails, or its last-update JSON generation breaks, or that step is silently dropped from its build. Site B builds fine and its notification arrives. The Filter reads site A's **stale** JSON, which still reports the previous change at 09:00. The newest archive (from that earlier change) has a key later than 09:00 → `found`, covered → silence. Every subsequent build repeats this against the same frozen timestamp.

**Concrete misbehaviour.** Every content change from 10:00 onward is unbacked-up, and the Coverage_Check reports the space as covered indefinitely. No email. Related door onto the same hole: a content change whose production build simply **fails** never republishes the JSON, so that change is invisible to both the trigger and the detector.

**Do the stated mitigations cover it?** No, and the residual-risk section doesn't name it. It records a broken Amplify topic (no invocation) but not a *fresh invocation against a frozen content timestamp*. There is no staleness guard on the Last_Update_API response anywhere in pass 2 — shape validation only (criterion 19.3), which a stale-but-well-formed payload passes.

**Fix.** Two parts, both quota-free:
1. Take `contentTs` as the **max across both production sites'** last-update endpoints (two template parameters, two fetches). One site's broken build then cannot freeze the comparison. This keeps the design's deliberate rejection of deriving the URL from the notification — these are fixed production endpoints, not the notifying branch's.
2. Treat a payload whose own build/publish timestamp is older than the notifying build's start as **stale**, log it, and fail open on the enqueue side. (Note the interaction with **K**: two fetches double the fetch budget.)

The structural fix remains the deferred Contentful-webhook trigger, and the decision record should say so — it is the only change that decouples detection from the build pipeline.

## C. HIGH — Retention expiry is not a redrive: an undelivered message vanishes with no DLQ hop and no email

**Scenario.** Criterion 3.1 sets `MessageRetentionPeriod ≥ 2 × VisibilityTimeout × maxReceiveCount`. With a 900 s backup timeout, visibility ≥ 6 × timeout = 5400 s and `maxReceiveCount` = 2, that floor is **6 hours**. If the design sets retention at or near that floor, an ESM disabled or throttled for more than six hours means the message reaches its retention limit.

**Concrete misbehaviour.** A message that expires by retention is **deleted by SQS**. Redrive to a dead-letter queue is triggided only by receive-count exhaustion, so the message never reaches the Dead_Letter_Queue, the Notifier never fires, and no email is sent. Composed with **A**, this is the complete-silence path: enqueue suppresses the coverage email, retention silently discards the request.

**Do the stated mitigations cover it?** No. The requirement expresses retention as a *floor* relative to the redelivery arithmetic, and the design treats the coherence question as closed by satisfying that floor. Nothing addresses the case where no receives happen at all.

**Fix.** Set retention to the maximum 14 days rather than to the computed floor. It is free, the redelivery arithmetic is still satisfied with an enormous margin, and it converts a six-hour silent-loss window into a fortnight during which **A**'s corrected suppression rule will surface the gap. Add a template comment saying the floor is a lower bound, not a target.

## D. HIGH — A broken or undeployed Notifier silences all three paths, and that is exactly its state on a first deployment

**Scenario.** The Notifier is the terminus of the DLQ path *and* the Filter's `OnFailure` destination. The design's "the placeholder now throws" change is described as converting the worst failure mode into the most visible one. For the Notifier the logic inverts: a throwing Notifier consumes the DLQ message, fails, is retried to the DLQ's own `maxReceiveCount`, and the message lands in the Terminal_Queue — which by design has **no consumer** and, with alarms forbidden by Requirement 11, no observer.

On a **first deployment** all three functions are simultaneously the placeholder. If the operator forgets `EventSourceMappingEnabled: false` (default is `true` per criterion 4.5), the backup placeholder throws → 2 redeliveries → DLQ → the Notifier placeholder throws → Terminal_Queue. Silence. Same outcome if the KMS grant turns out insufficient (the design's own open item #1): every publisher fails, the Backup_Lambda still throws per criterion 7.3, and the Notifier's publish fails too → Terminal_Queue → silence.

**Concrete misbehaviour.** The single function that all failure reporting funnels through has no backstop, and its own failure is routed to a silent sink.

**Do the stated mitigations cover it?** Partially and inconsistently. The design correctly identifies that the Terminal_Queue prevents head-of-line blocking, but presents it as a safety property without noting that its contents are unobserved. The KMS fallback ladder is gated on a commissioning test, which covers day one but nothing afterwards — if the topic is later re-created under a CMK, or the key policy changes, the whole channel goes dark with no signal.

**Fix.** Three cheap things:
1. Give the **Notifier** a placeholder that *publishes* "Notifier code was never applied" instead of throwing. Its role already holds `sns:Publish` + the KMS actions, and the runtime-bundled SDK is available to inline code. This is the one placeholder that must fail *open*.
2. Make the manual check in criterion 10.10 explicitly include reading `ApproximateNumberOfMessages` on the Terminal_Queue — currently 10.10 has no defined content, and terminal-queue depth is the only observable signal that notification is broken.
3. Record in the decision record that the Terminal_Queue is an unobserved sink and that this is accepted because Requirement 11 forbids the alarm that would watch it.

## E. HIGH — Archives the system itself judged bad satisfy the Coverage_Check, because the check reads only keys

Two distinct routes, same root cause: the check's `found` outcome is a statement about a key, and the key carries no verdict.

**E1 — the rate-limited partial archive.** Criterion 15.4 says an asset shortfall attributable to rate limiting **notifies but does not throw**; the archive is uploaded with `complete: false` in the manifest. The key lands and is now the newest key in the bucket. From that moment the Coverage_Check reports the content change as covered. Nothing ever re-attempts, nothing tracks the partial state, and the re-notify machinery in the suppression store keys on *content change*, not on archive completeness. The owner got one email saying "quota — wait", and waiting produces nothing, because the next backup only happens on the next content change.

**E2 — the verification-failed archive.** The upload completes, verification finds a size mismatch, the function throws (criterion 13.5). The **object is still in the bucket**, under a conforming key, and is now the newest key. No role holds `s3:DeleteObject` (deliberately, Requirement 40), so nothing removes it. Redeliveries produce a later key if they succeed; if they all fail, the DLQ emails once — and the poison key permanently suppresses coverage detection for that content state and every earlier one.

**Do the stated mitigations cover it?** No. Pass 2's justification for the key basis is entirely about `LastModified` being *later* than the export start; it never considers that a key can exist for an object the pipeline rejected. The three-outcome contract has no fourth state for "an archive exists but is not trustworthy."

**Fix.**
- For **E1**, write a partial archive under a key the `ARCHIVE_KEY` pattern **excludes** (e.g. `…Z.partial.zip`). Zero new state, zero new permission: the partial archive is still stored and still emailed, but it does not satisfy coverage, so the next build of either site re-enqueues — which is precisely the deferred retry the "wait for quota" remedy wants, arriving naturally rather than immediately. Document the suffix alongside the key format under criterion 13.3.
- For **E2**, have the Coverage_Check require `Size > 0` (and above a documented floor) from the listing it already performs — `ListObjectsV2` returns `Size` for free, including for Glacier objects. That catches truncation. A nonzero-but-wrong-size object cannot be fixed without a delete grant, so state it as an accepted limitation in the decision record rather than leaving it undiscovered.

## F. HIGH — A key that matches the pattern but fails to parse reads as "covered"

**Scenario.** `newestArchive` returns `{ state: 'found', at: timestampFromKey(newestKey) }`. `found` is decided purely by the regex; the parse result is never validated. The key form is `2026-09-19_14-06-01.123Z` — hyphens as time separators, which `new Date()` does **not** parse (it yields `Invalid Date`), so `timestampFromKey` must reconstruct it by hand.

**Concrete misbehaviour.** Any bug or edge in that reconstruction yields `NaN`. `NaN < contentTs − skew` evaluates to `false`, so the gap test fails, so the invocation is **silent** — the failure mode direction is the worst available one. The three-outcome contract lists "no content timestamp could be derived" under `indeterminate` but says nothing about an unparseable *key* timestamp.

**Do the stated mitigations cover it?** No. Criterion 49.2 identifies this exact class ("assert that a derived date is valid, because an equality assertion between two invalid results passes") for the property tests, but the design's own outcome contract does not encode it.

**Fix.** Add to the contract: a key that matches the pattern but does not parse to a valid date is `indeterminate`, with the reason logged. Assert `Number.isFinite(at)` at the boundary of the pure comparison function, which the design already extracts for testing.

## G. MEDIUM-HIGH — The skew tolerance is applied to the notification but not to the enqueue, and it is being asked to absorb *staleness*, which is a different quantity

**G1 — asymmetric application.** The notify condition is `keyTs < contentTs − skewTolerance`. The enqueue table says plainly "newest archive **older than content**" — no skew. That leaves a band `skewTolerance` wide in which the Filter **enqueues a redundant export but stays silent**. With `skew` = 60 s, archive key 10:05:00 and `contentTs` 10:05:20: enqueue fires (a full Contentful export for a change the archive already covers), notify does not. Because `contentTs` is static per content state, both sites' builds hit the same band.

Criterion 20.2's indefinite-dedup rule inherits the same defect — it says "a conforming backup **newer than** the content-change timestamp", with no skew term.

**G2 — skew vs. staleness.** Criterion 9.11 justifies the tolerance as "two independent clocks". Real NTP skew between Contentful and Lambda is seconds at most. But the design also describes `contentTs` as *"Contentful's, surfaced through a static build artefact"* — and build-artefact lag is minutes, not seconds. If the skew parameter is sized to absorb that lag, every second of tolerance is a second-wide window in which a content change made just after an export started is declared **covered** and, per 20.2, **not enqueued**: a permanently missed backup with no email. A 5-minute "skew" tolerance creates a 5-minute silent-miss window on every backup.

**Do the stated mitigations cover it?** No. Requirement 42.8 bounds the parameter but the design supplies no derivation, and nowhere states that the tolerance trades false alarms for undetected misses.

**Fix.** Apply `skewTolerance` identically in the enqueue comparison, the notify comparison and the 20.2 dedup comparison — ideally by routing all three through the single pure comparison function the design already extracts. Bound the parameter to a few seconds, justified by NTP, and state in the design that it is *not* the mechanism for build-artefact staleness (that is **B**'s freshness guard). Record the cost of the tolerance explicitly: a change landing within `skew` of an export start is silently treated as covered.

## H. MEDIUM — The suppression store's race is in the read, not the write, and Parameter Store cannot fix it

**Scenario (a), double-notify.** The design's claim is *"two frontends building at the same time write near-identical values, so the race is benign and needs no conditional write."* That is true of the **write** and irrelevant to the **decision**. The sequence is read → decide → publish → write. Two Filter invocations (the two sites' builds) whose reads both land before either write both see the old `lastNotifiedContentChange` and both publish. Two emails for one gap. The window is read-to-write, which spans an SNS publish — tens to hundreds of milliseconds, and wider on a cold start. This recurs at every re-notify boundary for a persistent gap, not just once.

It also fires without concurrency: a Filter killed after publishing but before writing (see **K**) leaves the store unwritten, so the next build re-notifies.

**Scenario (b), non-monotonic writes.** Last-write-wins has no ordering guard. Invocation A notifies for content state Y and writes `Y`; invocation B, working from a staler fetch, notifies for X and writes `X` afterwards. The store now records the *older* state, so the next build sees `Y ≠ X` and notifies for Y again. I could not construct a *never-notified* interleaving — the failure direction is consistently extra email, not lost email, which is the better of the two — but the "at most one" bound in criteria 9.16 and 7.10 is not achieved.

**Is last-write-wins actually safe? Does it need a conditional write?** It needs one, and the chosen store **cannot provide one**. SSM Parameter Store has no compare-and-swap; `Overwrite=false` is create-only, not CAS. So the design's statement that a conditional write is unnecessary is unfalsifiable as written, and the store choice forecloses the remedy. The rejection table dismisses DynamoDB as adding "a resource and a cost line to argue about" — but DynamoDB is the only listed option with a conditional write, and at one tiny item and tens of requests per year it is effectively $0 under the perpetual free tier. The real cost is one more resource, not money, and the design should say that rather than implying a price.

**Fix.** Choose deliberately and state it:
- Accept the bound honestly — amend 9.16/7.10 to "at most two emails per condition per re-notify interval" and document why (no CAS available); or
- Take DynamoDB with a conditional write for a genuine at-most-once guarantee, and record the resource (not dollar) cost.

Three adjacent gaps in the same mechanism, all currently undefined:
- **Malformed or initial suppression value.** `AWS::SSM::Parameter` requires a `Value`, so the parameter is created with a placeholder. Neither direction is specified, and both are bad: throwing emails a Filter failure on every build; treating it as suppressed never notifies. Specify: unparseable ⇒ no suppression, log at error level.
- **`PutParameter` failure after a successful publish** must be logged and swallowed, not thrown — a throw produces a second email (a Filter failure) on top of the coverage email it just sent.
- **CloudFormation reset.** The design rejects function tags and env vars because a write registers as drift and is reverted. The same mechanism applies, more weakly, to a template-declared SSM parameter: CloudFormation does not continuously reconcile, so the value survives ordinary updates, but any update that touches *that resource* (a Description or Tier change) reasserts the declared `Value`. Consequence is one extra email; worth one line in the design rather than an unstated asymmetry with the trap it just described.

## I. MEDIUM-HIGH — The FIFO DLQ's head-of-line block is bounded by two numbers the design never states, and batching can multiply the emails

**Does the terminal hop unblock the group or just delay the block?** It bounds it, and the bound is `maxReceiveCount_DLQ × VisibilityTimeout_DLQ`. Within a FIFO message group SQS will not deliver the next message until the current one is deleted or its visibility expires, and all messages here share a constant `MessageGroupId` inherited from the source queue. So a poison message blocks every subsequent failure notification for exactly that product.

**The problem.** Requirement 7.5 asks for a "low `maxReceiveCount`" and the design adopts it — but the multiplier that actually determines the block is the **DLQ's `VisibilityTimeout`**, which pass 4 never sets or discusses. The existing Dead_Letter_Queue was created as a plain DLQ; if it inherits the source queue's 1800 s (or is left at whatever it has) and `maxReceiveCount_DLQ` is 3, the block is **90 minutes** — on top of **J**'s 3-hour redelivery latency.

**Second, unaddressed hazard: batch blast radius.** The design specifies no `BatchSize` on the DLQ event source mapping and no `FunctionResponseTypes: ReportBatchItemFailures`. SQS ESM defaults to a batch size of 10, and without partial batch responses **one failing message returns the entire batch**. A single unprocessable message therefore causes the up-to-nine successfully-notified messages alongside it to be redelivered and **notified again**, once per retry round, for `maxReceiveCount_DLQ` rounds. That directly breaks criterion 7.10's one-email-per-message bound, and it is the design's own poison-message scenario producing duplicates rather than a block.

Third, minor: the DLQ is FIFO and inherits each message's original `MessageDeduplicationId`. Two failures for the same content state arriving at the DLQ within five minutes would be **silently dropped** by the DLQ's own dedup. Source-queue dedup makes this nearly unreachable, but the DLQ's dedup scope should be set explicitly rather than inherited by accident.

**Fix.** Set on the Dead_Letter_Queue and its ESM: `VisibilityTimeout` just above the Notifier's function timeout (a tiny function — timeout ~10 s, visibility 60 s), `maxReceiveCount_DLQ = 2`, and `BatchSize: 1`. Worst-case block drops to ~2 minutes, the terminal hop becomes precise, and batch-induced duplicates are impossible. Failures are rare, so throughput is not a consideration; ordering and blast radius are.

## J. MEDIUM — Worst-case notification latency is roughly 3–4.5 hours, is required to be stated, and is not

Requirement 3.7 requires the design to state worst-case notification latency per failure class. Pass 4 resolves the Filter time budget and never produces this number. The arithmetic:

A killed invocation (timeout/OOM — the class the Notifier exists for) consumes the **full visibility timeout** before redelivery. Criterion 3.3 fixes visibility ≥ 6 × the backup function timeout. With a 900 s backup timeout and `maxReceiveCount` = 2:

- first failure → DLQ arrival ≈ 2 × 5400 s = **3 hours**
- \+ DLQ head-of-line block, if any ≈ `maxReceiveCount_DLQ × VisibilityTimeout_DLQ` → up to **+1.5 h** on today's unspecified values (see **I**)
- caught-path failures, by contrast, email in **seconds**

So the design's fastest path covers the failures an operator could have found anyway, and the class the Notifier was built for is the slowest by three orders of magnitude.

The 6× multiplier is the direct cause, and it is inherited from Prior_Spec Requirement 20 rather than derived. For a *killed* invocation it buys nothing — the message is invisible for the whole window regardless — while multiplying crash-notification latency by six. A value just above the function timeout plus margin would cut the latency roughly fivefold.

**Fix.** State the latency table (per failure class, as a formula in the function timeout so it tracks the commissioning measurement). Either justify the 6× inheritance against its latency cost, or reduce it with a note that Prior_Spec Requirement 20 is relaxed for that reason.

## K. MEDIUM-HIGH — The Filter's time budget bounds the one call it controls and leaves the three AWS calls on SDK defaults

**The worst case, added up.** The design's invariant is "total time on Last_Update_API requests including retries and backoff ≤ half the function timeout", i.e. 15 s of 30 s. A 5 s per-request timeout × 3 attempts + 1 s + 2 s backoff = **18 s**, which already breaches the invariant. To fit, the per-request timeout must drop to ≈4 s with short backoff (12 + 3 = 15 s exactly). That is derivable, so the invariant is satisfiable — but only just, and **B**'s second endpoint would double it.

**The actual hole is the other half.** The remaining 15 s must cover a cold start with four SDK v3 clients (S3, SNS, SSM, SQS — the design states this function is *always* cold, so every invocation pays client construction and four fresh TLS handshakes), `ListObjectsV2`, `GetParameter`, `Publish`, and `PutParameter`. The design assigns that half a budget and then specifies **no timeout, no connection timeout and no attempt cap on any of the three AWS clients**. SDK v3 defaults to `standard` retry mode with 3 attempts and no short per-attempt deadline, so a throttled or slow S3/SSM/SNS call can consume tens of seconds on its own. The invariant is asserted over a half the design does not bound.

**Why that specific failure emails on every build.** A Filter timeout is an unhandled crash, not a fail-open. The async invocation fails, Lambda retries it (0–2 attempts per criterion 8.1, each paying the full 30 s), then the `OnFailure` destination fires the Notifier → **one email per build of either site, indefinitely**, for a condition with nothing to do with backup health. That is exactly the routine traffic criterion 57.13 forbids.

Note the contrast the design gets right: a genuinely slow *Last_Update_API* is safe, because an `AbortSignal` timeout is enforced and the fail-open path is silent by criterion 18.8. The email risk is concentrated entirely in the unbounded AWS calls and in the total, not in the endpoint the budget talks about.

**Fix.** Three changes:
1. Construct all three clients with an explicit `NodeHttpHandler` (`connectionTimeout`, `requestTimeout`) and `maxAttempts: 2`, with the values derived from the same budget as the fetch timeout.
2. Carry an **overall deadline** through the handler. When the budget is exhausted, the function must **return** — fail open, log at error level, no notification — rather than be killed. Budget exhaustion should be a silent fail-open path like every other Filter degradation; a timeout is the *only* Filter outcome that emails, so it must be unreachable by slow dependencies.
3. Actually compute the budget with the cold-start and handshake terms included, which is what criterion 16.9 asks for. "The current 30-second timeout is the value to validate against the measured latency of the static endpoint" is a deferral, not the computation the criterion demands.

Ordering note: the `PutParameter` write follows the publish inside the same budget, so a kill between them costs one duplicate email (see **H**). Publish-then-write is the right order — writing first would risk suppressing an email that was never sent — but the design should say so and count it against the one-email claim.

## L. MEDIUM — The enqueue decision table silently drops the update window, and the two possible readings are both defective

The enqueue table's columns are: status captured, branch matches, content timestamp, newest archive. There is **no update-window condition**. But criterion 42.5 constrains an update-window parameter (minimum = worst observed Amplify build duration plus margin), criterion 18.6 specifies fail-open behaviour when "the configured window value is absent or non-numeric", and criterion 0.3 forbids removing an existing parameter. So either the design dropped a live requirement without recording it, or the table — which is the normative decision specification — is incomplete. Both readings produce a real defect:

- **Window dropped.** The two sites' builds for one content change often finish more than five minutes apart (SQS dedup window). The second build sees the same `contentTs`, and the listing cannot see the backup that is still mid-export (the key only appears on successful upload), so criterion 20.2's "indefinite dedup" fails and a **second full export** is enqueued. That is an increase on the success path, which criterion 0.6 forbids outright. It also means the design's claim that 20.2 "suppresses indefinitely rather than for five minutes" holds only once the archive has landed — the in-flight window is `export + archive + upload duration − 5 min` wide, on every content change.
- **Window retained.** The second build does not enqueue, so coverage condition 3 no longer suppresses, and if `now − contentTs` exceeds the grace period the owner is emailed a gap for a backup that is **currently running or has just finished and not yet uploaded**. This is the false-positive case.

**Fix.** State the enqueue table completely, including the window and its interaction with the listing comparison. Apply **A**'s stateful suppression so that an enqueue-in-flight is covered by a grace window rather than by an instantaneous veto, and apply **G**'s skew term to the 20.2 comparison so the in-flight window is not also a silent-miss window.

Related, and also missing: **the grace period has no derivation anywhere.** Criterion 9.12 requires it to be "long enough to accommodate a build plus a backup in flight", and criterion 42.5 already obliges the *window* minimum to be measured against real Amplify build durations. The design should state `grace ≥ worst build duration + worst export + archive + upload + margin` and take the build figure from the same measurement. Without it, the parameter that decides between spam and silence is an undocumented default.

## M. MEDIUM — "Retain the newest archive unconditionally" is not expressible in an S3 lifecycle configuration, and pass 4 silently omits it

Criterion 34.9 requires two things: a retention minimum no shorter than the longest recorded quiet interval, **and** that the configuration "retain the newest archive unconditionally". Pass 4 implements only noncurrent-version expiry, delete-marker removal and MPU abort. It never mentions the second clause.

It cannot. S3 lifecycle predicates are age, prefix, tag and size — there is no "newest object" predicate. Tagging the newest object would need `s3:PutObjectTagging`, which Requirement 40 does not grant and which cuts against Requirement 36's immutability intent. So the criterion is unimplementable as written, and the failure it guards against is severe: if every archive expires during a long quiet period, the listing returns `none`, criterion 9.8 makes that a determinate gap, and the owner is emailed a coverage gap **on every subsequent build** for a space that is merely quiet — breaching 9.14 and 57.13 through a legitimate parameter value.

**Fix.** Do not expire current versions at all. Expire noncurrent versions, remove expired delete markers, abort incomplete multipart uploads, and let current archives persist. At 8–25 backups a year and tens of megabytes each, total steady-state storage is a few gigabytes — the current-version expiry buys almost nothing and creates the whole hazard. This satisfies 34.9's intent structurally rather than by parameter constraint, removes the "every archive expired" failure mode entirely, and simplifies the storage-class minimum-duration arithmetic in criterion 34.6.

## N. MEDIUM — The listing algorithm takes no prefix, so criterion 9.19's hook is unimplemented and `indeterminate` can latch on permanently

Two problems in one signature. `newestArchive(s3, bucket)` accepts no prefix:

- **Criterion 9.19** requires the bucket listing prefix to be configurable, and **criterion 10.4** depends on that hook to create a coverage gap for verification without deleting an archive (for which no role holds permission). As written, the verification step in 10.4 has no mechanism.
- **`MAX_PAGES` is a latent off-switch.** The listing is flat and unprefixed — it enumerates every object in the bucket and filters afterwards. The "25–75 objects, two orders of magnitude below one page" argument holds for *archives*, not for the bucket. Should anything else ever accumulate there, the listing exceeds 5 pages and returns `indeterminate`, which by criterion 9.9 **never notifies**. The coverage detector switches itself off permanently, silently, for a reason unrelated to backups. The same latch is reachable via a `ListBucket` permission change or a mis-scoped bucket-policy TLS deny.

**Fix.** Add the prefix parameter to the algorithm signature and pass it to `ListObjectsV2` — it satisfies 9.19, enables 10.4, and makes `MAX_PAGES` unreachable. Separately, resolve the tension in 9.9: a *single* indeterminate result must stay silent, but **sustained** indeterminacy across N consecutive builds is a real unresolved condition, not an inability to check, and should notify. The suppression store already exists to count it. Without that, "indeterminate" is a permanent silent failure state by design.

(The loop itself is correct — `pages` increments in the condition so exactly five pages are read before `indeterminate` — so the comment matches the behaviour.)

## O. MEDIUM-HIGH — The Notifier cannot satisfy criterion 7.11 on the DLQ path, and no correlator exists

Criterion 7.11 requires every notification to carry the failing phase, the UTC timestamp, the space and environment, the error message, and the log stream identifier plus the query to read it. On the DLQ path the Notifier receives the **original backup request** — nothing about the failure. It cannot know the phase (the throw happened in a different function), cannot know the error message, and cannot identify the failed invocation's log stream (the message carries no request id of the invocation that died).

Worse, the log groups are `INFREQUENT_ACCESS`, so `GetLogEvents`/`FilterLogEvents` are unavailable and the notification must supply a **Logs Insights query** — which needs a field to filter on. There is none. The design specifies no correlator between an SQS message and the Backup_Lambda's log lines.

The DLQ path is the one covering timeout and OOM: exactly the failures where an operator has nothing else to go on. As designed, the email reads "a backup failed, somewhere, for unknown reasons."

**Fix.** Require the Backup_Lambda to log `messageId`, `MessageDeduplicationId` and the current phase as structured fields on entry and on every phase transition (Requirement 11 already routes operational values into structured logs, so this is free). The Notifier then emits a Logs Insights query filtering the backup log group on that `messageId` over the retention window. Record in the design that the DLQ-path email carries the *query* rather than the phase, because the phase is only knowable from the logs the query retrieves.

## P. LOW-MEDIUM — The `ApproximateReceiveCount` gate is sound here, but the "exactly one email" claim is stronger than the attribute guarantees

Working through the three sub-questions:

- **Is the count reliably 1 on first delivery?** In this topology, mostly yes — and more reliably than the name suggests. A constant `MessageGroupId` on a FIFO queue means the ESM will not have a second message of that group in flight, so the usual inflation route (a receive whose invocation is throttled or fails before the handler runs, incrementing the count without an execution) is largely precluded. I could not construct a likely path to a count of 2 on the true first delivery in this design.
- **Can it reset and send several?** SQS documents the attribute as approximate and warns it can be inaccurate in rare cases. If it reads 1 twice, the result is 2 caught-path emails plus 1 DLQ email. With `maxReceiveCount` = 2 the worst case is **3 emails**, not the 1 that criterion 7.10 asserts ("at most ONE email per failed message from the caught-error path... achieved from the `ApproximateReceiveCount` attribute, requiring no stored state"). The design repeats the claim as settled: *"the gate needs no state and no extra call."* An exact bound cannot be derived from an attribute documented as approximate.
- **If the first delivery is killed by timeout before it can publish?** The designed behaviour works: no caught email (the publish never ran), count 1 consumed; second delivery sees 2, the gate suppresses, the failure recurs, count reaches `maxReceiveCount`, DLQ → Notifier → **exactly one email**. The cost is latency, not silence — see **J** (≈3 h).

**Fix.** State the bound as "≤2 caught-path emails plus 1 DLQ email in the pathological case, normally 1", and note that an exact bound would require per-`messageId` state, which the design deliberately declines. With `maxReceiveCount` bounded to 2 the blast radius is three emails, so declining is the right call — but the requirement's language should be corrected rather than the guarantee overstated.

## Smaller items

- **Fail-open with no derivable branch is undefined.** Criterion 18.1 requires a branch match before a fail-open enqueue, but the branch is derived from the app URL in the message body — so a malformed body yields no branch. The design's step 1 says "malformed record body → fail open, no notification", with no branch check. If that enqueues, a benign upstream format change spends a Contentful export on every build of every branch (bounded to one per grace window by criterion 18.10, but still). Specify the direction explicitly.
- **A failed `SendMessage` is undefined against the coverage suppression.** Condition 3 is written on intent. Criterion 20.5 forbids inferring an enqueue from a successful send, and criterion 8.8 says the Filter throws on error — so a send failure should throw and email via the async path. Say so, otherwise a failed enqueue both fails to back up and suppresses the gap email.
- **The manual-remedy command in criterion 9.21** can be deduplicated against an enqueue the Filter already made (5-minute window). Realistically an operator acts hours later, so harmless — but if an earlier enqueue is still undelivered (see **A**/**C**), the manual send adds a *second* message and produces two exports once the path is restored. One line in the email's wording ("check the queue depth first") covers it.
- **Cold-start cost of four SDK clients** on an always-cold function is never accounted for anywhere — not in the time budget (**K**), not in the Filter's `MemorySize` (criterion 16.7 requires it declared on every function; the design adds the parameter but no value or basis). The commissioning export sizes the Backup_Lambda; nothing sizes the Filter, whose workload this specification materially increased.
- **Filter `ReservedConcurrentExecutions` has a trap.** Criterion 16.8 requires the property on every function. If the Filter's value is set to 1 to paper over **H**'s race, a concurrent second build is throttled; a throttled *async* invocation is retried and, on exhaustion, fires the `OnFailure` destination → an **email about a Filter failure** caused by two sites building at once. The value must be ≥ the number of consuming sites plus margin, and the design should say why.

## What I'd fix first

**A**, **B**, **C** and **D** compose into a single narrative: the system can fail totally — no backup, ever — while emailing nothing, and three independent mechanisms each contribute a link (suppression-by-intent, a frozen content timestamp, retention-without-redrive, and a terminus with no backstop). None of the four appears in the design's "What no path covers" section, which is the artefact criterion 11.12 obliges to be exhaustive. Fixing **A** alone (stateful, grace-bounded suppression on the store that already exists) converts the worst case from permanent silence into one email per re-notify interval, and it is the cheapest change on this list.
